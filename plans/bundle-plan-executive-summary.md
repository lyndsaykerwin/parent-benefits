## What Bundle is

A phone website for middle-class parents in any US state who are expecting or have a new baby. One calm page: money they can get back, benefits with deadlines, recalls on things they bought, and deals truly worth it. Behind it, AI helpers (`agents`) look things up, argue over tricky offers and double-check every number. All demo data is made up.

## The headline idea: the Living Fine-Print Database (Strategy 2, decided, must-do)

**In one line:** the agents' own conclusions about offers become a new data source that Zetaris searches next to the government sources.

- **What gets saved.** Each time the Fact-Checker and the Fine Print Court judge an offer, they save one row to `offer_checks` in our online database (`Neon`). (In the Court a Deal Hunter argues for an offer, a Fine Print Lawyer against, and a Judge rules; the Judge fills the old "Parent Panel" role.) A row holds the offer, its hidden strings ("$8 shipping", "renews at $29.99/month"), the effort to claim it (account, app, mail-in, phone call, steps, minutes), the product's recall status and when checked, the grade (true value and the time to get it), the exact fine-print quote, and a wording **fingerprint** (`fine_print_hash`) so any change is noticed. No family column.
- **Real rows, never loose files**, added as a Zetaris source with its "add this table" command (`REGISTER DATASOURCE TABLE`).
- **The newsroom loop: the plan's systematic feedback loop, the visible one in this draft (round 4c), and it needs no users.** Like a newsroom: the maker agents file, the Fact-Checker edits, and the archive (`offer_checks`) shapes the next story. Each offer's detailed grade (value, minutes, steps, payout wait, claim window, catches) is saved, then fed back through Zetaris (past grades) and Meterless memory (grading lessons) into how the agents grade the next offers. When the Fact-Checker confirms or corrects a grade, the lessons used are marked right or wrong, so better ones come first. Unchanged wording reuses the saved grade (decided). **The same rows also feed the data product below** (`v_offer_audit` + `/api/offer-audit` with its OpenAPI description, still must-do and on Sunday's timeline): the newsroom loop does not replace or demote it.
- **Numbers come from code** (dollars, dates, yes/no flags); the AI writes only soft fields like the summary, which code checks. Every dollar must come from the quoted fine print.
- **Questions across sources:** "Which offers did our agents rate truly free, where the product hasn't been recalled since we checked?" joins `offer_checks` with live recalls from the product-safety agency (`CPSC`) and the FDA's data service (`openFDA`). The Coach asks: "Which fine-print problems show up most in 'Report issue' clicks?"
- **Value Score: value and the time to get it (decided, round 4c); both together decide "worth your time".** For example "Worth $40 after strings attached · about 15 minutes · paid within 8 weeks", not "20% off": true value (`true_value_cents`), effort minutes and steps (`effort_minutes_estimate`, `steps_count`), payout wait (`payout_wait_days_max`) and claim window (`claim_window_days`), all already in `offer_checks`, plus an effort badge and the catches. Time isn't turned into dollars (that needs a made-up hourly rate). This replaces a per-offer "confidence score". The exact "worth your time" cut-off is an open proposal.
- **Verdicts:** approve, "approve with a catch" (`approve_with_catch`), reject; a code "reject" beats an AI "approve." 12 fine-print tests (hidden shipping, expired, mail-in rebate, auto-renew, minimum purchase, fine print that gives the AI orders (`prompt injection`), more) plus 3 good offers that must pass.
- **The data product (decided, must-do, on the timeline):** read-only `GET /api/offer-audit?store=...`, a fixed question on a saved Zetaris view of per-brand totals only (`v_offer_audit`: catch rate, true vs. advertised value, effort), with a request cap (`rate limit`) and an **OpenAPI description** (the standard file telling any program or AI agent how to use it). A test checks no family fields leak. About 2–3 hours.
- **Pitch slide only:** selling this data, and "Points Guy"-style brand report cards (Strategy 3). No brand portal. A plug-in letting AI agents use the tool (`MCP server`) comes later.

## How the agents work together: the loops (plan section 1b)

Judges reward agents that check each other, send work back and retry, not ones that run once in a line. Lyndsay's goal: truly teamwork-based agents without a slow screen or big AI bill. A **loop** sends work back with a reason; every loop has a hard limit. **Her design (decided):**

- **Shared workspace ("bus") in Meterless memory. PLANNED.** A whiteboard where Clawback Hunter, Recall Checker and Benefits Planner post ideas, which go to the Court, then the Fact-Checker. **Meterless's memory engine (`H-MEM`) holds it:** every claim, question and correction is saved as a note with its source, a trust number and an audit trail judges can read. **Plain code** still decides which agent goes next, delivers questions, and enforces round caps and time limits; no Meterless engine does that. H-MEM runs inside our server with no AI call, so it adds milliseconds. Today H-MEM holds only approved rules; agents share one run context and trace log (`AgentContext`) but don't message each other.
- **Clawback Hunter ↔ Recall Checker (safety-value). PLANNED.** Before showing a price drop or rebate: "is this item recalled?" A real CPSC or FDA recall kills the deal before the Judge.
- **Benefits Planner ↔ Fine Print Lawyer (eligibility). PLANNED.** The Lawyer tries to disprove a benefit (timing, conditions, income caps) and sends back a counter-question ("ask Zetaris for X first").
- **Judge ↔ Fact-Checker (targeted correction), max 2 rounds. BUILT, basic form:** wrong cards go back to their maker with the reason and corrected values, and the Court re-judges (`orchestrator.ts` 225–261, `finePrintCourt.ts` 187–197). Line-by-line wording planned.
- **The newsroom loop (database loop). PLANNED (must-do).** When Judge and Fact-Checker agree, save the verdict, `status`, `rule_citations` and the value-and-time grade to `offer_checks`. Next run, agents ask Zetaris first and skip offers already rejected by a rule for everyone, or whose fingerprint is unchanged (decided); other offers are graded with past grades and Meterless lessons in hand. Misses become tests. **Later (decided):** parent taps tuning a confidence number.

**Also built:** the **Court debate** (one round; the Judge cites approved rules from memory, `case law`; a rebuttal round is an open proposal) and **Coach learning** (small: parent reports → proposed rule → owner approval → Judge must use it). **Open proposals (agent-added):** a **photo check loop** (code checks the vision model's reading, one retry, then ask for a close-up) and a **recall check loop** (Fact-Checker verifies each match against the record; no evidence, no alert).

**Keeping it fast (Lyndsay's design, all planned).** Live Zetaris runs took 13–171 seconds; each AI call stops at 20 seconds with no retry, and the feed shows only when the run ends. Her design: **the last verified feed appears instantly**; a **1–2 second fast path** (simple rules, active recalls) **streams high-confidence cards**, urgent recalls first; **deep loops run in the background** and push updates ("New savings verified!") by **server-sent events** (`SSE`, one-way server-to-browser push; `WebSockets`, a two-way line, is the alternative); **status pills** ("Recall Checker cross-referencing CPSC feeds…"); background checks add, update or remove cards. Today the "Checking" screen polls real agent steps each second. **Limits:** round caps (corrections 2, fixed debate rounds, 5 offers per run: built; photo retry 1: proposed); per-call time limit plus one retry and a 300-second run limit (`RUN_DEADLINE_SECONDS`; planned, must-do, decided); four agents run at once, Zetaris filters first, fast model for debate and bigger one for the Judge, saved answers in sample mode (all built); skip the AI when a saved verdict applies (planned; unchanged-wording skip decided); the Meterless workspace adds milliseconds, not AI calls (planned).

## Strategy 1: the Virtual Household Profile (decided: the existing Matcher, story told better)

Nothing is built differently: the Matcher asks Zetaris one question combining the family's stage, date and state with the rules and approved offers. Pitch line: *"Zetaris does the filtering, so the AI gets a short, already-checked list instead of the family's whole history: fewer tokens, lower cost, less room to make things up."* (A token is a chunk of text; AI services charge per token.)

## Getting purchases in: photo first (decided)

1. **Photo: the hackathon priority.** A label, a formula can's bottom or a paper receipt; an NVIDIA picture-reading model (`vision model`) turns it into a structured row Zetaris can join. Candidates: `nemotron-nano-12b-v2-vl`, `nemotron-3-nano-omni-30b-a3b-reasoning`, `nemotron-3.5-super-vl-120b-a12b` (default open). The phone strips hidden location data (`EXIF`); the AI rejects photos of people or addresses; the photo is deleted after reading.
2. **Email receipts: kept for after the hackathon (Lyndsay's decision).** Forwarded to the agents' **Agentmail** inbox; code keeps only item rows, discards names, addresses, card digits and raw text, deletes the email; "Use sample receipts" button.
3. **Barcode: kept for after the hackathon (Lyndsay's decision).** `barcode-detector` library, "type the numbers instead" backup, names from Open Food Facts then UPCitemdb.

All land in `purchase_items`, seen by Zetaris only through a safe-columns view (`v_purchase_items`) joined with live recalls. **Why photo (live feeds, Oct 24):** codes hide in recall *text*. CPSC's model-number field is empty in all 739 recalls since June 2025, yet about 50 of 86 baby recalls name the model in the description; only 22 of 739 give the barcode number (`UPC`). For formula, 31 of 42 FDA recalls list the UPC and 36 of 42 the lot code (batch number on the can). Matching tries exact codes first (UPC, model, lot), then brand and product words.

**FDA recalls stay.** Only the 17 of 42 *finished* ones (`Terminated`) are filtered out, so no parent gets a scary card about a recall that ended years ago.

## Zetaris and the other sponsor tech

- **Zetaris** (required "data door"): one database question (`SQL`) reads several places at once; it stays the only way agents read data. Each helper gets its own filtered window (`privacy views`); the Judge never sees family data. Two places still read the database directly (family profile; Coach reading reports); routing them through Zetaris is an open proposal. Without Zetaris, no personal card can be made.
- **Meterless:** its memory engine (`H-MEM`) stores approved rules the Judge must cite (built), and will hold the agents' shared workspace and the newsroom loop's grading lessons, with its own right/wrong feedback (planned). Its long-task (`Markovian`) and shared-facts (`World Model`) engines aren't used: our AI steps are short and Zetaris already holds the shared facts. **Nightshift** (Meterless's app turning Lyndsay's Mac into a private AI server) is the main AI route and hands hard steps to **NVIDIA Nemotron**.
- **Nightshift's job, in plain English.** Nightshift is Meterless's free Mac app that acts as Bundle's AI switchboard: every AI question the agents ask goes to Nightshift on Lyndsay's Mac, which passes it to NVIDIA's Nemotron using her NVIDIA key, stored inside Nightshift (never in our code). That makes it the "primary AI provider" the Meterless rule asks for. It is separate from Meterless memory (`H-MEM`), which stores learned rules and shared findings. In the cloud the code talks to a stand-in; Lyndsay switches the real one on at her Mac. Not yet confirmed (`research-nightshift-setup.md`): the menu for adding the key, where its password file lives, pinning one exact model with "thinking" off (due Sunday), whether replies name the real model, NVIDIA credit and rate limits.
- **Nightshift (decided):** all code built and tested in the cloud against a fake Nightshift server (proven: right labels, stuck calls cut off, wrong password refused, server error retried). Lyndsay switches it on at her Mac (`progress/reviews/cloud-build-assessment.md` §4). Live AI runs and the video happen on the Mac; a fresh download replays saved answers (`SAMPLE_MODE=true`), as the README says.
- **Standing rules:** Neon, not Supabase; no Redis (agents write to Neon, screens read Neon); never claim "real-time". **Parent feedback is not the focus** (no users at launch); the built Coach and learning demo stay as is.
