# Lane C QC: the photo reader (Oct 26, 2026)

Independent check by a reviewer who did not build it. Nothing was edited except this report and the screenshots in `progress/reviews/lane-c-qc-screens/`.

**Bottom line:** the photo reader works live. In real mode (real NVIDIA AI, real Neon database) it read 4 of 4 example photos correctly, gave a plain answer for a picture with no label in about 10 seconds, and answered every upload in under 0.3 seconds. In a phone-width browser, the Gear Locker showed "Reading…" and then the item. All 5 done conditions pass. There are **no blockers**. There are 2 medium fixes worth doing before judging:
- a photo stuck as "Reading…" for 15 minutes after a server restart;
- a queue with no size limit.

## Findings by severity

### Medium

1. **After a server restart, a photo shows "Reading…" for 15 minutes.**
   - **What I saw:** I sent photo 37, stopped the server, then started it again. The photo still came back as `status:"reading", canRetry:false`. "Try again" gave `410 gone` ("please take it again").
   - **Why:** the record is only marked "interrupted" when someone looks at it, and only after 15 minutes (`STALE_READING_MS`, `photoJobs.ts:26` and `:138`). So a parent watches a spinner for 15 minutes. Render's free tier restarts and sleeps the server often, which makes this likely.
   - **Fix:** when the server starts, mark every photo still marked "reading" as interrupted in one database update:
     ```sql
     UPDATE item_photos SET status='failed', read_error=INTERRUPTED_MESSAGE, updated_at=now() WHERE status='reading'
     ```
     This is safe because a fresh server holds no reading jobs. Also, in `view()`, treat any "reading" record that this server has no job for as interrupted straight away, whatever its age.
2. **The queue has no size limit, and every waiting photo stays in memory.**
   - **Why:** `queue` (`photoJobs.ts:63`) can grow without end. Each waiting job holds up to 5 MB of picture data. The 30-per-15-minutes limit applies to each connection, not to the whole server. When NVIDIA is busy, one photo can take up to about 20 minutes: 4 tries of up to 4 minutes, plus 3.5 minutes of queue waits. Meanwhile the server reads only 2 at a time, so photos pile up. A handful of testers could fill the memory of Render's free tier, which is 512 MB.
   - **Fix:** in `start()`, refuse new photos when the queue holds more than about 20 jobs (or about 60 MB of pictures). Answer with code 503 ("busy right now") and the plain message "Lots of photos right now. Please try again in a few minutes." Optionally also limit each family to about 3 waiting photos.

### Low

3. **A database error after a read leaves the photo stuck forever and never frees its memory.**
   - **Why:** after a successful read, the code saves the result (`describe` and `updatePhoto`, `photoJobs.ts:108-114`). In the failure path, `finish()` saves the status (`:95`) before it wipes the picture. If either save fails, the error is silently dropped (`pump` at `:89`, `.catch(() => undefined)`). The picture is then never wiped. The record stays "reading". And because a job is still held in memory, the "interrupted after 15 minutes" rule never applies (`!job` at `:138`), so it shows "Reading…" until the next restart.
   - **Fix:** wrap the body of `run()` in a try/finally. In the finally part, wipe the picture or keep it for "Try again". If the save failed, set the record to failed in memory, and log the error with `console.error` instead of dropping it.
4. **The memory of finished duplicate photos is never cleared.** `finished` (`photoJobs.ts:64`) only ever grows. It holds each result plus its small picture. **Fix:** delete each entry after about 10 minutes (use the same timer as `keepForRetry`), or once the client has asked for it.
5. **The backup model is not "only when busy".** The builder's report says the backup is tried whenever the main model is busy. The code (`llm.ts:370-384`) also moves to the backup after a timeout, a server error, a connection error, or a missing model (404). This is reasonable behavior, but the report and comments should say it. **Fix:** change the comment at `llm.ts:346` and the build report to match.
6. **A picture with no label is told "please send a clearer photo".** The model said there was no text at all, so the answer should not blame clarity. **Fix:** in `photo.ts:533`, when the model's reason mentions no text or no label, use a different message, for example "We couldn't find a label in this photo. Point the camera at the white sticker with the model number." The model already returns that reason.
7. **On the Savings tab, the gear locker card contradicts itself while a photo is being read.** For a family with nothing in the locker yet, it says "No gear yet — scan a car seat sticker…" and also "Reading 1 photo…" (screenshot `03a-savings-card-reading.png`). **Fix:** in `GearLocker.tsx:166`, show the empty-locker text only when `n === 0 && reading === 0`.
8. **Repeated code.** The older direct `/api/photo/read` route repeats the checks that `parseUpload()` already does (`photoRoutes.ts:132-137` vs `:95-103`). **Fix:** have that route call `parseUpload()`. Also, `retry()` (`photoJobs.ts:184-187`) checks the same three conditions twice; compute "busy" once.
9. **The full recall checker still ignores the date made.** `server/agents/recall.ts` reads purchases through Zetaris's `v_purchase_items` view, and that view has no `manufactured_on` column. Only the photo-time check uses the date. The builder disclosed this. **Fix:** add the column to the Zetaris view, or leave it as a known limit and mention it in the demo script.
10. **"Practice mode, no keys" is not truly key-free.** `server/env.ts:10` loads `.secrets/bundle.env.local` by itself. Practice mode still replays the recording, because `isLiveModel()` needs `LIVE_MODEL=true`, but keys are present in memory. This is only a note for anyone testing a keyless setup.
