## (b) Tightness

- **Zetaris still does real work: yes.** Both questions still go to Zetaris live in real mode (trace evidence above). The double-check question still combines two different tables (`state_programs` and `tax_parameters`) in one query, which is the part that shows off Zetaris. The only thing moved from Zetaris into code is a one-line check that the rule's state equals the family's state (`benefits.ts:107`, `eligibilityLawyer.ts:66-72`), on tables of 8 and 7 rows. That does not hollow out the sponsor requirement.
  - Small cost to the story: Zetaris now returns every state's rows, and the app throws most of them away. If a judge asks, the honest answer is: "one fixed question, so it can be replayed safely."
- **SQL injection (sneaking harmful text into a database question): safer than before.** The family's state no longer goes into any SQL. `ruleCheckSql` uses `quoteId`, which only allows `[A-Za-z0-9_.:-]` and throws on anything else (`sql.ts:12-16`). `offerCheckSql` passes the id through `Number()`. The rule codes recorded come from the database, not from users.
- **The `'federal' AS state` workaround: correct.** `rowsForState` keeps every row whose `source` is not `state_program` before it even looks at the state (`eligibilityLawyer.ts:68`). So the label on tax rows is cosmetic and can never wrongly include or drop a row. Live Zetaris accepted the query.
- **Secrets and personal data in the recordings: clean.** 219 files. A search for email addresses found none. A search for `api_key|bearer|secret|password|token|nvapi-|sk-…` found nothing. The only `"email"` strings are a purchase source label (`"source":"email"`). The only `employer` value is the made-up "Buckeye Logistics". 8 files are new. Of the 30 changed files, 27 differ only in the recorded response time (`ms`). The other 3 have real data changes:

- **Dead code:** none found. `rulesSql(state)` and `eligibilityCounterSql(state)` have no callers left with the old argument.

## Findings by severity

**Medium: none. High: none.**

**Low 1: the stateNote blocker is confirmed, but the client covers for it.** At `bundle/server/routes/bundleRoutes.ts:167-174`, `parentResult()` copies `familyId, runId, receipt, banner, cards, blocked, offersOnFile` but **not** `stateNote`. `orchestrator.ts:425` sets that field, but it never reaches a parent. In practice the screen still shows the note: `client/src/lib/tabs.ts:110-117` (`comingSoonNote`) falls back to the family's state against `COVERED_STATES = ['CA','MA','NY']` (`client/src/lib/onboarding.ts:7`), and both `/api/run` and `/api/runs/:id` return `family`. The real risk is two lists of covered states that can drift apart. **Fix:** in `parentResult` add `...(r.stateNote ? { stateNote: r.stateNote } : {})`, plus a test in the route tests.

**Low 2: the recording script copies text and logic from other files with no test guard.** It contains:
- `ALL_OFFERS_SQL` (`scripts/zetaris/record.ts:35-36`), a copy of the court's query (`finePrintCourt.ts:300,308`)
- `offerCheckSql` (`record.ts:40-41`), a copy of the Fact-Checker's offer query (`factChecker.ts:117`)
- `COURT_MAX_OFFERS = 5` (`record.ts:38`), a copy of `MAX_OFFERS` (`finePrintCourt.ts:13`)
- `generalOfferSets` (`record.ts:51-64`), which mirrors the court's offer selection (`finePrintCourt.ts:316-319`)

Only a loose pattern check (`/v_judge_offers WHERE id = 4$/`) covers these. If the fine-print lane changes the court's columns or limit, practice mode stops finding saved answers and no unit test fails; only the all-states replay test catches it, after a re-record. **Fix:** export `judgeOffersSql()`, `offerCheckSql()` and `MAX_OFFERS` from the agents and import them in `record.ts`, the same way `ruleCheckSql` is already shared.

**Low 3: the Fact-Checker still keeps its own copy of the rule query** (`factChecker.ts:99`), even though `ruleCheckSql` now exists (`benefits.ts:40-42`). A test guards it (`allStatesReplay.test.ts:108-115`). **Fix:** call `ruleCheckSql(String(claim.ref))` there.

**Low 4: the saved-grade question still depends on which offers a family's age picks** (`savedVerdictsSql(set)`). It works only because `generalOfferSets` pre-records every possible set of offers, checking every age from -400 days to the oldest offer's age plus one. A due date more than 400 days away would miss, though the form probably can't produce one. **Fix (offers lane):** make it one fixed fetch-all question and filter in code, as the builder suggested.

**Low 5: untested paths.**
- `rowsForState` keeps a row that has no `state` column at all (`eligibilityLawyer.ts:70`, `st === undefined`). This only matters for older saved answers, and no test covers that branch.
- `generalOfferSets` with an empty offer list, and with offers whose age window is negative (before birth), is untested.

**Low 6: a live data change slipped into the saved answers.** Re-recording also updated the report-card answers (Amazon 3→4 checked). That is harmless, but anyone reviewing the commit should know the saved report card changed.
